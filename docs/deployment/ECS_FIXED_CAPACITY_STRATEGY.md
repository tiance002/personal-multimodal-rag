# 固定配置 ECS 的后续执行策略

2026-10-23 Owner 决定：现有 ECS 云盘性能作为固定边界，后续任务不以升级云盘或实例为前提。本策略用于后续部署和隔离验收；沿用现有 HTTP、Registry、SendGate、LocalExecution、权限、来源和 UNKNOWN 合同。

## 已知配置与证据边界

以下是本次恢复后的单次采样，不是压力测试或内存峰值。源码基线为 `419f5d19bf578701e91ab41d07f48776d8081ec7`；运行中的生产 API/Worker 仍使用镜像 `sha256:80e2f2d84bf67d7d22117d98676049aa9cd3101e69b20f780d5fd9eeaf931a36`，本策略没有发布新应用版本。

| 项目 | 2026-10-23 00:00 左右（Asia/Shanghai）的已验证值 |
|---|---|
| 主机内存 | 约 3.5 GiB；恢复后 MemAvailable 约 2.7 GiB；没有 swap |
| CPU | 实际 `nproc=2`；不给应用附加未经需要的 CPU 配额 |

| 云盘 IOPS、吞吐、延迟 | `NOT_RECORDED`；历史控制台有 I/O 受限告警，不能从磁盘占用推断性能余量 |

不据此增加应用内存限额、创建 swap 或调整 P5、模型、检索阈值、RRF、Schema 和索引。实际任务的用量结算和权限保护仍由原执行链负责。

## 执行顺序和并发

1. 本机先完成源码修改、定向离线测试和构建输入检查。ECS 只承接需要其真实 PG/Redis、来源和正式 HTTP 的验收，不在 ECS 重复整仓测试。
2. 同一 ECS 同时只运行一个评测批次，每次只提交一道问答。已有主任务未结束时，不再启动第二个批次、导入、Embedding 重算、索引构建、大量导出或 Docker 构建。
3. 每个源码/profile 批次复用一个隔离临时 API，串行执行已批准的问题；不逐题创建 API 容器。同题需要独立 Session 时照常创建新 Session。不同版本或权限合同不能为了复用而混用。
4. API/Worker 保留既有资源配置。只构建和更新实际受影响的服务，兼容底座已证明一致时沿用增量构建；构建和评测错峰。Docker CPU 参数以实际内核支持为准，不再把不支持的 NanoCPUs 当启动前置条件。
5. 批次启动前确认没有另一个活跃批次。当前 runner 的锁是每个 job 的锁，**尚未实现跨 job 的主机级互斥**；现阶段由执行代理核对并遵守单批次规则，不能宣称程序已全局限并发。

Owner 随后明确要求充分使用 CPU 和内存。以上互斥针对评测调度与高磁盘负载，不把整台主机降为单线程：没有磁盘重负载时，独立的 CPU 计算可以使用实际两个核心；互不共享事务的轻量任务可在内存容得下时并行。并发依据实际工作集、cgroup 事件和 `MemAvailable` 调整，不人为要求长期空出大块固定内存，也不把容器 memory limit 当作已预分配内存。保留系统与 PG/Redis 正常工作的余量，避免在低性能磁盘上同时制造多个大读写流；不为提高利用率而并发使用同一 PG 连接的事务。

## 控制内存与磁盘工作量

- 镜像、源码、依赖、来源范围和服务身份在批次开始时核对一次；逐题仍执行原权限、当前版本、引用和账本校验，但不重复枚举全部历史容器或导出整库指纹。
- 不在生产 API/Worker 的共享 cgroup 内用 `docker exec` 运行整库导出或重型分析。必要的只读检查使用独立进程/容器，查询限定到实际问题所需的文档、Chunk 和字段；采用游标/流式读取，避免一次载入整库和重复嵌套元数据。
- 原始请求、响应和调用收据保存单份；每题只补充查询、来源 ID、终态、真实 Token 和结果摘要。问题诊断需要的大对象按需保存，不为每个阶段复制整份 Context、parser_metadata 或历史语料。
- 新 runner 将空闲 `RUNNING` 心跳持久化从每秒一次改为每 15 秒一次。子进程仍每秒轮询；启动、终态、原有逐题检查点、单次启动 claim、Provider 账本和收据继续按原合同及时持久化。不能为了省 I/O 取消结算或 UNKNOWN 的耐久写入。
- 运行时按需读取小状态，通常不必比 30–60 秒更频繁；不持续下载日志全文。runner 的终态 `status` 会重算产物哈希，因此结束后做一次稳定导出和哈希核对，避免反复扫描同一份完整结果。
- 不新增任意文件大小/数量上限，也不截断原始证据。容量控制靠限定本次范围、避免重复副本和完成后的明确归档；必要的大文件继续流式复制/哈希。

15 秒心跳意味着空闲状态提交的理论频率从每分钟 60 次降到 4 次；这不是已测得的 IOPS、吞吐或端到端延迟改善。

## 脱离本机与结果生命周期

按 [后台任务入口](ECS_ACCEPTANCE_BACKGROUND_JOBS.md) 使用同一持久任务根目录，收到 `start_acknowledged=true` 后即可断开本机。ECS 保留日志、逐题结果、账本和最终产物；本机恢复后读取，不依赖持续 SSH 会话。

任务完成后：

1. 生成并取回一次稳定的结果清单及 SHA；在本机确认文件齐全、哈希一致、账本可回读。
2. 标记本次结果已归档，保留源码、镜像、profile、Session/调用身份和原始收据；失败、UNKNOWN 和未结算记录仍保留。
3. 后续若需回收空间，只列出本次明确创建、已停止且已完成证据归档的临时容器、重复传输包或构建目录，再执行具名清理。清理能力不等于本次已获删除历史资产的授权；当前没有删除旧容器、镜像、数据卷或历史收据。
4. Owner 已决定暂不创建 OOS 自动清理任务。将来若重新启用，只对专用临时目录中已结束、已归档核验的旧日志设置规则，排除活跃任务和未归档证据。不把 `[PRIVATE_PATH_SHA256:d3473a18fbb95efb28c0a92ba1a045237f2288928f5e36b781ee49101872240c]`、`[PRIVATE_PATH_SHA256:85c72baabd17d4a9baeda44a2fe12366279b6d035ac1306e66e88b9fec633739]`、数据库目录或 `/` 交给通配清理；不以 `prune`、`down -v`、截断容器日志或删除 PG WAL 来释放空间。

临时目录清理只回收空间，不能证明云盘 I/O 限制已消失。当前磁盘 48% 使用率也不能证明任意评测负载都可承受。

## 负载异常与重启

- 批次开始、结束记录一次主机可用内存、磁盘占用和目标容器状态；确有资源诊断需要时再以小样本记录运行中 cgroup 用量/事件。缺少峰值就写 `NOT_RECORDED`，不为补指标重发已完成问答。
- 出现持续资源压力、OOM 或 I/O 受限时，停止调度下一题，先让已发送的调用完成结算。进程被杀或发送结果不明时保留原 request ID/UNKNOWN，只读对账；不杀掉在途调用后自动重试。
- Redis 的 `run_id` 随进程重启变化。重启后先核实仍是正确的 Compose Redis、持久卷、DB8/前缀及 PG 物理身份，再同步 `runtime.env` 的预期值并只恢复受影响应用；不盲目接受任意新 Redis。此轮已完成手工恢复，**尚未安装自动身份同步/重启续发服务**。
- 强制停止后的本次 PG 日志显示 WAL redo 完成，Redis AOF 加载/写入状态正常；这是本次恢复证据，不是未来强停的数据安全保证。后续停止实例前先停止新任务并等待在途调用结算，随后正常停机。
