**这是给执行端的防跑偏备忘录。**本文件不是要求重新研究几个月，也不能取代完整 Goal。

## 1. 已获用户确认（必须执行）

| 决策 | 结论 | 验收意义 |
|---|---|---|

| 评测 | 公开六数据集与 Gold 边界保留 | 独立比较 Cheap、Expensive、动态路由；真实问答/Gold 不得伪造 |

| 临时实验 | V4/G4 探针与预算门、V6 Grant、饱和输出凭据不属于新正常问答 | 保留审计历史，在获批准的切换后退出主链 |
| 非必要特性 | WeKnora 全部外围功能（IM、沙箱、企业管理等）非本轮必须全部移植 | 以现有知识库问答所需主链和历史/记忆完整闭环为目标 |

**不能把“只保留两个创新”理解成可以关闭 KB 权限、支付预算、数据隔离或者清理 UNKNOWN。**也不能为了保留旧的高级安全校验而继续保留旧 Chunk/Prompt/Validator 的业务判断。

## 3. 源码对齐时最容易错的事实

### 3.1 上游 Pipeline 不是一个固定不变的串行列表

`internal/application/service/session_knowledge_qa.go` 实际根据 KB/Web/Agent/History 等条件构建插件；`query_understand.go` 有 `EnableRewrite` 或图片才启用的分支；`search.go` 的 Expansion 又有额外数量条件。**不要强迫每个问题都做 Rewrite、Hybrid 或 Rerank。**

主要文件：
- `internal/application/service/session_knowledge_qa.go`
- `internal/application/service/chat_pipeline/query_understand.go`
- `internal/application/service/chat_pipeline/search.go`
- `internal/application/service/chat_pipeline/query_expansion.go`
- `internal/application/service/chat_pipeline/rerank.go`
- `internal/application/service/chat_pipeline/merge.go`
- `internal/application/service/chat_pipeline/filter_top_k.go`
- `internal/application/service/chat_pipeline/into_chat_message.go`

### 3.2 配置中存在不同层次的默认值

固定 `config/config.yaml` 显式定义 `embedding_top_k=30`、`vector_threshold=0.2`、`keyword_threshold=0.3`、`rerank_top_k=30`、`rerank_threshold=0.3`、`enable_rewrite=true`、`enable_query_expansion=true`、`enable_rerank=true` 和 `summary.max_completion_tokens=1024`；而 `internal/types/retrieval_config.go` 部分方法有单独的默认值（例如 `DefaultRetrievalTopK=50`、向量阈值 `0.15`、RerankTopK `10`、RerankThreshold 的 fallback），RRF 默认 `k=60`、向量/关键词 `0.7/0.3`。**按调用来源与覆盖次序取值，不能“看到了50就全局改成50”，也不能因源文件有配置字段就认为请求一定启用。**

### 3.3 模型输出的底层协议字段不能猜

`internal/models/api/openaicompletions/request.go` 根据 provider compat 决定 `max_tokens`/`max_completion_tokens`、stream usage、thinking 等；`transport.go` 中实际静态默认非流式 300 秒、流式 600 秒，上层已有 deadline 时不覆盖；注释有陈旧数值，**请按可执行赋值而不是注释**。不用复制旧 output probe 的硬校验算法。

### 3.4 同为 BM25 不等价于同一检索结果

上游 Postgres `internal/application/repository/retriever/postgres/repository.go` 走 `paradedb.score`/ParadeDB；现有 Python `backend/app/adapters/postgres/knowledge_repository.py` 使用自定义 `chunk_terms` SQL BM25。分词、文档长度统计、阈值与索引过滤都可能不同。**优先在隔离数据库采用上游方式；若不装同一索引扩展，必须报告明确偏差并通过离线对照，不准声称完整一致。**

### 3.5 直接完整流式 UX 与 Cheap 先校验后升级存在冲突

上游可以即时把模型 tokens 推向 SSE；Cheap 若流到前端后又被判失败升级，会留下两份互相冲突的答案。必须局限在新增 Router 的输出缓冲/提交协调层处理，记录为**两项自研机制的必要差异**，而不是重新设计整个 WeKnora SSE 体系。

### 3.6 旧 P5 升级默认值不能不声不响更改

`RouterPolicy` 当前阈值 `0.35`；`quality_escalation=true`，普通云配置 `truncated_escalation=true`，`abstention_escalation=false`，`provider_fallback=false`。因此历史 Xing `REQUEST_TIMEOUT` 没有自动 DeepSeek 升级是符合旧配置的。用户同意保留升级机制**不等于授权将所有供应商超时都默认改成自动双模型付费调用**。新算法去掉旧在线 Regex Validator 后，升级判据要改为真实、可观察的传输/响应/引用信号；未通过的新语义判断不得默默塞回去。

### 3.7 基准不包括线上供应商必然成功

WeKnora 的 Go/Python 可观察行为对齐能够减少自研协议差异，但无法保证 Xing/DeepSeek 的网络吞吐、供应商排队或计费。真实验收必须区分：`SOURCE_PARITY`、`PROVIDER_AVAILABLE`、`ANSWER_QUALITY`、`COST_LEDGER_CONFIRMED`、`DEPLOYED_REVISION`。

## 4. 真实运行版本与已经发生的历史故障

最新远端 `55372f7` 将尚未验收的流式候选做了检查点；此前报告给出**当时**在线镜像仍是 `ce3398a`。旧普通题与短题由 DeepSeek 升级后 PASS；长题有一次预算未准入，后两次 Xing 分别 90/120 秒超时并形成 UNKNOWN，最新任务停止。**这些只能用于保留历史和构造合成回放，不能声称新 Python WeKnora 主链已经解决。**

任务开始后生成只读身份报告，并在每阶段报告中区分 `HEAD`、`WORKTREE`、`DEPLOYED_IMAGE`、`DATABASE_MIGRATION`、`CONFIG_REVISION`、`REAL_RUN`。

## 5. 需要用户后续单独确认的操作，不阻塞离线编码

- 将 `provider_fallback` 从 false 改为 true（Cheap 超时是否自动升级）及其可能产生的额外费用。
- 任何新的真实供应商请求、真实 Caption/OCR 云端调用、公开长题回放、新增任务额度。
- 将新实现挂载到当前服务、增加当前生产数据库扩展、重建真实索引、迁移旧业务资料/记忆。
- 解除 V4 最新 UNKNOWN 停止条件、发布/推送、删除旧数据。

**执行端不需要再问“是否保留动态路由”**：已明确必须保留并正式接主链。其他缺少用户新许可的动作不执行即可，能做的隔离代码与测试继续推进。
